## Pro의 핵심 판단

Bindery의 문제는 화면 장식이 부족한 것이 아니라, 외부 약속이 넓고 데이터
상태가 뭉뚱그려져 있어 사용자가 “지금 지원 가능한가, 어떤 조건이 비었는가,
다음에 무엇을 해야 하는가”를 즉시 판단하기 어렵다는 점이다. 따라서 외부
카피는 `지금 지원할 수 있는 창작 행사`로 좁히고, 내부 자산은 장기 회차
레지스트리로 유지한다.

### 즉시 고칠 결함

1. 출처 접근 가능, 참가 판단 가능, 편집 검수를 서로 다른 데이터 상태로 표시한다.
2. 종료된 신청 마감에 `D-DAY`를 붙이지 않고 현재·과거를 분리한다.
3. 비교는 비어 있는 상태에서 시작하고 사용자가 2~3개를 직접 고르게 한다.
4. 다른 통화·부스 크기·VAT 조건을 `최저가`로 순위화하지 않는다.
5. 부스 옵션 전체와 필드별 충족도를 노출하고 빈 섹션은 압축한다.
6. 아카이브는 실제로 두 개 이상 회차가 연결된 시리즈만 보여 준다.
7. Binder 저장 뒤 비교·일정·준비 작업으로 이어지는 다음 행동을 제공한다.
8. GitHub Pages는 동작하는 앱처럼 보이지 않는 읽기 전용 스냅샷이어야 한다.
9. 홈·커뮤니티의 광고 예약 공간과 독립 업계 News 확장은 현재 제거한다.
10. 런타임 Google Fonts 요청을 없애고 네트워크 장애에도 유지되는 글꼴
    스택을 사용한다.

### 지금 확장하지 않을 것

- Creator OS·업체 비교·계산기를 핵심 행사 흐름보다 먼저 구현
- 운영 근거 없는 광고, 유료 노출 또는 추천 순위
- 외부 Supabase·Turnstile 구성 없이 커뮤니티를 실제 서비스처럼 표현
- 소스가 열린다는 이유만으로 마감·비용·환불·사업자 조건을 검수 완료로 승격

## 적용한 성공 지표와 다음 게이트

코드 완료 여부와 제품 검증을 분리한다. 다음 확장 전에 아래를 실제 사용으로
확인한다.

- 핵심 사용자 인터뷰·관찰 5명 이상
- 참가 판단 가능한 회차 15개 이상
- 목록→상세, 상세→공식 원문, 저장→다시 열기, 저장→ICS/비교 전환율
- 출처 변경→재확인 완료 시간과 핵심 필드 누락률
- Binder 재방문과 저장 행사별 준비 작업 사용

외부 사용자 조사, 운영 런타임 구성, 프로덕션 분석 계측은 이 저장소 수정만으로
완료할 수 없다. 해당 증거가 생기기 전에는 커뮤니티·광고·Creator OS를 성장
전략으로 승인하지 않는다.

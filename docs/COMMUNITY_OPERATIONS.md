# Community Operations

이 문서는 바인더리 커뮤니티의 구현·운영 기준이다. 제품 약관이나 법률
자문을 대신하지 않는다. 아래 보존 기간과 개인정보 처리 기준은 개발용 운영
기본값이며, 실제 사용자 접수 전 제품 소유자의 개인정보 처리방침 및 법률
검토로 확정해야 한다.

## 운영 원칙

1. 커뮤니티의 목적은 반응량을 늘리는 것이 아니라 문구 작가가 다시 찾을 수
   있는 실무 정보를 축적하는 것이다.
2. 작가 자격과 정보의 사실성은 분리한다. 작가 상태는 게시판 활동 자격만
   표시하며, 게시글의 정확성은 출처·확인일·정정 이력으로 판단한다.
3. 권한은 서버와 데이터베이스에서 기본 거부한다. URL, 브라우저 저장값,
   화면 배지, 클라이언트 요청값은 권한 근거가 아니다.
4. 공개 게시와 신고는 운영자가 처리할 수 있는 범위에서만 연다. 실제
   접수에는 운영 대기열, 알림, 조치 사유, 이의제기와 감사 기록이 함께
   존재해야 한다.
5. 필요한 정보만 수집한다. 첫 작가 신청에서 신분증, 사업자등록증, 주소,
   전화번호, 정산 정보와 비공개 파일을 받지 않는다.

## 역할과 접근

계정 역할과 작가 상태는 별도로 관리한다.

### 계정 역할

- `member`: 일반 로그인 회원
- `moderator`: 게시글·댓글·신고 운영 담당자
- `admin`: 역할, 작가 상태, 초대, 정책과 전체 운영 담당자

### 계정 상태

- `active`: 정상 이용
- `suspended`: 모든 작성과 보호 게시판 접근 중지
- `deleted`: 로그인과 신규 활동 중지, 삭제 정책에 따라 데이터 처리

### 접근 표

| 사용자 | 모두의 게시판 | 작가 인증 게시판 | 운영 화면 |
|---|---|---|---|
| 비회원 | 읽기 | 접근 불가 | 접근 불가 |
| 정상 회원 | 읽기·쓰기·댓글·신고 | 접근 불가 | 접근 불가 |
| 임시 승인 작가 | 전체 이용 | 읽기·제한적 쓰기 | 접근 불가 |
| 검수 완료 작가 | 전체 이용 | 전체 이용 | 접근 불가 |
| 운영자 | 전체 이용 | 운영 목적 접근 | 신고·콘텐츠 운영 |
| 관리자 | 전체 이용 | 운영 목적 접근, 작가 상태가 있을 때 작성 | 인증·초대·역할·정책 운영 |

정지·삭제 계정은 작가 게시판을 읽거나 쓸 수 없다. 거절·정지·회수된 작가
상태는 작가 참여용 읽기·쓰기 권한을 주지 않지만, 활성 운영자·관리자의 운영
목적 읽기 권한은 계정 역할에서 별도로 판단한다. 그 밖의 보호 콘텐츠는 잠금
화면의 HTML, 메타데이터, 검색 결과에도 포함하지 않는다.

## 작가 신청 상태

```text
미신청
  → provisional(임시 승인 · 검수 대기)
  → verified(검수 완료)
  → rejected(거절)
  → suspended(일시 정지)
  → revoked(회수)
```

- 유효한 신청을 제출하면 같은 요청 안에서 `provisional` 상태와 운영자
  검수 항목을 함께 만든다.
- 사용자 화면에는 반드시 `임시 승인 · 검수 대기`라고 표시한다.
  `인증 완료`, `공식 인증`, `정보 검증`이라고 표시하지 않는다.
- 검수 목표는 제출 후 7일 이내다. 7일을 넘긴 항목은 운영 대기열에서
  지연 상태로 표시한다.
- 임시 승인 중 작가 게시판 제한은 계정당 24시간에 새 글 1건, 댓글 5건을
  기본값으로 한다. 운영자는 스팸·안전 사유로 더 제한할 수 있지만 조치
  사유를 남겨야 한다.
- 거절·정지·회수는 다음 서버 권한 검사부터 즉시 작가 참여용 읽기·쓰기
  권한을 제거한다. 활성 운영자·관리자의 별도 운영 읽기 권한에는 작가 상태를
  사용하지 않는다.
- 동일 공개 증빙 URL의 중복 신청과 동일 요청 재전송을 막는다.
- 신청, 재신청, 상태 변경은 bot 검증, 속도 제한과 멱등성 검사를 통과해야
  한다.

## 최소 신청 정보

필수:

- 공개 활동명
- 공개 활동 증빙 URL 1개
- 주요 활동 분야
- 현재 커뮤니티 운영 규칙 및 개인정보 처리방침 동의

선택:

- 공개 판매처 또는 행사 참가 URL
- 운영자에게 전달할 짧은 설명

URL은 정규화한 뒤 중복을 검사한다. 비공개 서류와 첨부파일은 받지 않는다.
추후 파일 증빙을 도입하려면 별도의 개인정보 영향 검토, 비공개 저장소,
파일 형식·크기 제한, 악성 파일 검사, 접근 기록과 삭제 정책을 먼저
확정한다.

## 운영자 초대

- 첫 출시에서는 `admin`만 초대를 발급할 수 있다.
- 초대는 이메일 또는 지정 계정에 연결한 일회용 토큰이며 기본 7일 뒤
  만료된다.
- 운영자가 이미 활동 사실을 확인한 대상은 초대 수락 시 `verified`로
  전환할 수 있다.
- 수락자는 현재 커뮤니티 정책 버전을 확인하고 체크박스로 명시적 동의를
  제출해야 한다. 동의하지 않았거나 초대의 정책 버전이 오래됐으면 초대·
  인증·정책 동의 행을 변경하지 않는다.
- 초대 발급, 재발급, 수락, 만료, 취소에는 발급자·대상·시각·사유를
  남긴다.
- 회원 간 초대와 추천인 보상은 첫 출시 범위에 포함하지 않는다.

## 게시글과 정보 기준

게시글 상태:

```text
draft → published → under_review → hidden / locked → deleted
```

- `모두의 게시판`은 공개 열람, 정상 회원 작성·댓글·신고를 기본으로 한다.
- `작가 인증 게시판`의 일반 참여는 활성 `provisional` 또는 `verified`
  상태만 읽고 쓸 수 있다.
- 활성 `moderator`와 `admin`은 작가 게시판을 운영 목적으로 읽을 수 있지만,
  자신의 작가 상태가 활성 `provisional` 또는 `verified`가 아니면 글·
  댓글을 작성할 수 없다.
- 질문에는 미해결·해결 상태를 둘 수 있다.
- 사실 안내에는 출처 URL, 출처 이름과 확인 날짜를 입력할 수 있다.
- 경험담과 공식·사실 안내를 시각적·의미적으로 구분한다.
- 오래된 출처는 최신 정보처럼 보이지 않도록 재확인 필요 상태로 표시한다.
- 운영자 노트로 승격할 때 원본 게시글, 작성자, 출처와 승격 시점을
  유지한다.

## 신고와 운영 조치

신고 상태:

```text
open → triaged → actioned / dismissed → appealed → closed
```

- 회원은 같은 대상·사유에 대한 중복 신고를 만들 수 없다.
- 신상 노출, 즉각적인 위해, 사기·결제 피해처럼 긴급한 신고는 24시간 내
  1차 확인을 목표로 한다.
- 일반 신고는 영업일 3일 내 1차 확인을 목표로 한다.
- 숨김, 잠금, 복구, 경고, 계정 정지, 작가 상태 변경에는 운영자와 사유가
  필수다.
- `moderator`는 콘텐츠와 신고를 처리할 수 있지만 역할 부여, 작가 인증
  확정, 초대 발급은 할 수 없다.
- 운영 조치는 기존 기록을 덮어쓰지 않고 감사 로그에 추가한다.

## 정정, 삭제와 이의제기

- 작성자는 자신의 공개 글을 수정할 수 있으며 중요한 사실 변경은 수정
  사유와 함께 이전 제목·본문 스냅샷으로 남긴다.
- 운영자는 잘못된 정보에 제목·본문 정정을 적용하고, 공개 출처를 다시
  확인한 경우 기존 출처를 덮어쓰지 않고 새 확인 행을 추가한다. 최신
  확인일의 출처가 목록·검색·지식화 화면에 사용된다.
- 정정으로 글의 갱신 시각이 바뀌어도 검색 목록은 순위, 갱신 시각, 글 ID로
  구성한 불투명 커서를 사용한다. 다음 페이지 링크는 검색·게시판·분류·
  해결·신선도 필터를 유지한다.
- 일반 삭제는 소프트 삭제다. 목록과 본문에서는 내용을 숨기되 신고·운영
  이력과 삭제 시점을 유지한다.
- 개인정보 삭제 요청과 계정 삭제는 별도 운영 절차로 처리한다. 법적 보존
  의무가 없는 개인정보는 삭제하거나 비식별화하고, 보존이 필요한 최소
  감사 정보만 분리한다.
- 거절·정지·회수·콘텐츠 숨김 조치의 이의제기는 통지 후 14일 내 접수할 수
  있다. 운영자는 접수 후 7일 내 1차 답변을 목표로 한다.
- 이의제기는 숨김·잠금·계정 정지를 만든 정확한 운영 조치에 연결한다.
  승인 시에도 그 뒤에 추가된 숨김·잠금·삭제·계정 정지를 되돌리지 않는다.
- 관리자는 이의제기를 인용해 아직 유효한 원 제한만 복구하거나, 기각해 원
  제한을 유지할 수 있다. 두 결과 모두 별도 운영 조치·감사·수신자 알림으로
  남긴다. 일반 `restore`도 해당 신고가 만든 현재 제한만 되돌릴 수 있다.
- 수정 이력의 공개 화면은 편집자·사유·시각만 제공한다. 이전 제목·본문은
  익명 및 일반 인증 회원의 직접 조회 대상이 아니다.
- 이의제기를 심사한 운영자는 원 조치 담당자와 같을 수 있지만, 동일인이
  처리한 경우 감사 로그에 그 사실을 표시한다.

## 개발용 보존 기본값

다음 값은 실제 서비스 전 법률·개인정보 검토가 필요한 개발 기본값이다.

- 활성 프로필과 작가 신청: 계정 또는 작가 상태가 유지되는 동안
- 거절·회수 신청의 공개 URL 및 운영 메모: 이의제기 종료 후 30일
- 중복·남용 방지용 비가역 URL 지문: 최종 처리 후 180일
- 종료된 신고·운영 조치·감사 기록: 종료 후 1년
- 삭제된 게시글 본문과 수정본: 삭제 후 30일 뒤 비식별화 또는 제거
- 읽은 알림: 90일

운영자는 보존 만료 작업 결과를 기록한다. 데이터베이스 백업과 첨부 저장소
백업은 별개이므로, 향후 파일 저장을 도입할 때는 각각의 복구·삭제 범위를
문서화해야 한다.

## 구현 및 배포 경계

- `supabase/migrations/`의 파일명 순서가 스키마 배포 순서다. foundation,
  인증 워크플로, 일반 게시판, 작가 제한, 운영 콘솔, Binder, 지식화, 검색,
  알림, 작가 신청 보안 강화, 콘텐츠 무결성·이의제기, 정정·페이지네이션,
  수명주기 무결성 마이그레이션을 일부만 선택해 적용하지 않는다.
- 로컬 검증은 `scripts/test-community-db.sh`가 만드는 격리 PostgreSQL 17
  클러스터에서 모든 production 마이그레이션을 적용한다. 이는 RLS와 RPC의
  실제 데이터베이스 증거지만, 외부 Supabase의 Auth 메일·Turnstile·백업·
  네트워크 설정을 검증한 결과는 아니다.
- 외부 프로젝트를 승인받아 연결하기 전에는 Sites 런타임에 Supabase URL,
  publishable key, Turnstile site key를 넣지 않는다. 작가 신청은 Supabase
  Edge Function이 Turnstile secret을 한 번만 검증한 뒤 service-role 전용
  RPC를 호출한다. `service_role`과 Turnstile secret은 Edge Function 밖이나
  브라우저 공개 환경변수에 두지 않는다.
- 백엔드 미구성 환경은 공개 예시 글과 기기 초안을 표시하되 회원 변경을
  저장한 것처럼 보이지 않는다. 구성된 환경은 읽기 실패 시 예시 글로
  조용히 대체하지 않고 오류 상태를 보여 준다.

## 운영 루틴

1. `/admin/community/verifications`에서 `임시 승인 · 검수 대기`와 7일 지연
   항목을 확인하고 공개 증빙 URL을 검수한다.
2. `/admin/community/reports`에서 긴급 신고를 먼저 분류한 뒤 모든 숨김·잠금·
   복구·기각에 구체적 사유를 남긴다.
3. `/admin/community/audit`에서 인증, 초대, 신고와 운영 조치가 별도 감사
   사건으로 남았는지 확인한다.
4. 공개 사실 글과 해결된 질문의 출처 확인일을 점검한다. 오래된 항목은
   운영자 정정에서 새 출처 확인 행을 추가하고, 해결·출처·공개 상태를 모두
   만족하는 일반 게시판 질문만 유지보수 Note로 승격한다.
5. 사용자에게 전달되는 커뮤니티 알림은 `/me/notifications`의 계정 내
   알림이다. 이메일이나 외부 호출이 필요한 업무는 별도 운영 채널에서
   확인하며 현재 코드가 발송했다고 간주하지 않는다.
6. Binder 동기화는 사용자의 명시적 합치기 요청만 처리한다. 부분 실패 시
   기기 저장을 유지하고, 계정 행을 대량 삭제하거나 양방향 덮어쓰지 않는다.
   행사 저장은 데이터베이스 카탈로그를 통과하며 계정당 100건으로 제한한다.
7. 숨김·잠금·계정 정지 알림의 이의제기는 영향받은 작성자만 14일 안에
   제출할 수 있다. 사유는 신고자에게 공개되는 신고 행과 분리해 보관하며,
   `resolve_appeal`은 관리자만 처리한다. 처리 전 이의제기 대상 조치 이후의
   추가 제한이 있는지 확인하고, 데이터베이스의 인과적 복구 결과를 감사
   기록과 대조한다.
8. 이벤트 연결은 `community_event_allowlist`의 현재 제품 카탈로그와
   `app/lib/data.ts`를 함께 갱신한 뒤 전체 마이그레이션/RLS 테스트를 다시
   실행한다. 임의의 문법상 유효한 이벤트 ID를 게시글에 연결하지 않는다.

## 백업과 복구 경계

- 외부 운영 전 Supabase 프로젝트의 자동 백업 주기, 복구 지점, 복구 담당자,
  복구 훈련 날짜를 제품 소유자가 별도로 확정한다.
- 게시글 소프트 삭제와 데이터베이스 백업 삭제는 다른 작업이다. 개인정보
  삭제 요청은 활성 테이블, 수정 이력, 감사 최소 정보와 백업 만료 시점을
  각각 기록해야 한다.
- 현재 저장소에는 외부 백업 생성·복원 자동화가 없다. 로컬 RLS 테스트 성공을
  운영 백업 또는 재해 복구 증거로 사용하지 않는다.

## 운영 전 필수 확인

- 제품 소유자가 약관과 개인정보 처리방침을 확정했는가
- 수집 항목, 처리 목적, 보존 기간과 국외 이전 여부를 고지했는가
- 운영자 연락 경로와 신고·이의제기 알림이 실제로 도착하는가
- 권한별 RLS 테스트와 서버 권한 테스트가 실제 Postgres에서 통과하는가
- 백업, 복구, 개인정보 삭제와 사고 대응 절차를 시험했는가
- 광고·분석 스크립트를 붙이지 않은 상태로 커뮤니티를 먼저 운영하는가
- 검색에서 비인가 작가 글과 숨김·삭제 글이 나오지 않는가
- 다른 회원이 알림 목록이나 읽음 상태를 조회·변경할 수 없는가
- 기기 Binder 합치기의 중복·부분 실패 후 로컬 데이터가 보존되는가
- 인증 회원이 artist 신청 테이블이나 legacy 신청 RPC를 직접 호출해 임시
  승인을 우회할 수 없는가
- 신고자 또는 다른 회원이 작성자의 이의제기 사유를 읽을 수 없는가

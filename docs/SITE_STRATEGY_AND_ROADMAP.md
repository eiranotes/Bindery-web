# Bindery 사이트 전략 및 실행 로드맵

기준일: 2026-08-02  
대상 저장소: `eiranotes/Bindery-web`  
상태: 제품 전략 정본 및 단계별 구현 기준

## 2026-08-11 적용 메모

WebGPT Pro 전체 재검토 결과, 이 문서의 행사 우선 전략은 유지하되 외부 약속과
다음 개발 순서를 더 좁힌다. 외부 첫 문장은 `지금 지원할 수 있는 창작 행사`에
집중하고, `행사 데이터베이스이자 운영 지식 아카이브`는 내부 장기 모델로 둔다.

단순히 공식 URL이 열리는 70개 회차를 동일한 품질로 세지 않는다. 편집 검수,
참가 판단 핵심 필드 충족, 출처 접근 가능, 재확인 필요를 분리하고 다음 확장의
게이트를 아래처럼 고정한다.

1. 핵심 사용자 5명 이상의 탐색·비교·저장·준비 관찰
2. 참가 판단 가능한 회차 15개 이상
3. 목록→상세→공식 원문과 저장→재열기·비교·ICS·준비 전환 측정
4. 출처 변경 재확인 시간과 핵심 필드 누락률 측정

이 증거 전에는 Creator OS, 업체 비교·계산기, live Community 성장, 광고·유료
노출을 다음 핵심 제품으로 승인하지 않는다. News는 독립 미디어가 아니라 행사
변경 기록으로 제한하고 GitHub Pages는 서버 기능 없는 읽기 전용 스냅샷으로
운영한다. 세부 구현 결정은 D-037~D-040을 따른다.

## 0. 결론

Bindery의 장기 경쟁력은 자유게시판의 글 수나 일반적인 콘텐츠 발행량이 아니라,
**한국 독립 문구·일러스트 창작 행사의 회차별 조건과 변화가 같은 구조로 누적되는 데이터 자산**에서 나온다.

제품의 중심을 다음과 같이 고정한다.

> Bindery는 한국 독립 창작자가 어떤 행사에 지원할지 결정하고, 지원부터 현장 운영까지 준비하도록 돕는 행사 데이터베이스이자 운영 지식 아카이브다.

이에 따라 제품 계층을 다음 순서로 운영한다.

1. **행사 데이터베이스**: 유입과 검색의 중심
2. **회차 아카이브·비교·저장·일정 도구**: 재방문을 만드는 핵심 도구
3. **노트**: 반복 질문을 유지보수 가능한 지식으로 정리하는 계층
4. **커뮤니티**: 데이터의 공백과 실제 경험을 보충하는 계층
5. **뉴스**: 핵심 작업을 보조하는 제한된 정보 계층

공동구매는 후단 작업으로 미루고 정책·신뢰·신고 기준이 승인될 때까지 공개
탐색, sitemap, 정적 배포 산출물에서 숨긴다.

커뮤니티 기능은 이미 강한 안전·권한 기반을 갖추었지만, 실제 운영의 다음 병목은
백엔드 기능 추가가 아니라 **검증된 실제 행사 데이터의 양, 최신성, 비교 가능성**이다.
향후 개발 우선순위도 이 순서를 따라야 한다.

## 1. 현재 저장소 진단

### 1.1 현재 컨셉

현재 Bindery는 다음 기능을 한 사이트에 통합한 정보 바인더다.

- 행사 신청 마감과 참가 조건
- 회차별 행사 상세와 지난 회차 비교
- 실무 노트와 공식 공지 색인
- 읽기 전용 공동구매 현황
- 작가 인증 게시판과 공개 게시판
- 기기 및 계정 Binder
- 일정 구독, RSS, 검색, 알림, 신고, 운영·감사 기능

기능 범위만 보면 작은 MVP를 넘어 이미 운영 플랫폼의 기반에 가깝다. 특히
Supabase Auth/Postgres/RLS, 권한 분리, 신고·이의제기·감사 이력, 검색과 알림은
초기 트래픽 규모에 비해 상당히 앞서 있다.

### 1.2 강점

| 영역 | 현재 강점 | 장기 가치 |
|---|---|---|
| 제품 철학 | 공식 원문과 확인 시점을 우선하고 정보 경계를 명확히 표시 | 신뢰 브랜드 형성 |
| 행사 모델 | 마감, 참가비, 사업자 조건, 현장 정보, 회차 이력, 후기 공개 기준을 구조화 | 비교·검색·추천의 원천 데이터 |
| 디자인 | 리소 인쇄를 장식이 아니라 구조선·타이포·제한된 색 역할로 번역 | 범용 SaaS와 구분되는 시각 정체성 |
| 계정 없는 도구 | URL 필터, ICS, 기기 Binder | 가입 전에도 즉시 가치 제공 |
| 커뮤니티 안전 | 인증 상태와 운영 역할 분리, RLS, 실패 폐쇄, 감사 이력 | 실제 UGC 운영 시 사고 비용 감소 |
| 기술 품질 | 서버 렌더링, SEO, JSON-LD, sitemap, RSS, 반응형·접근성 테스트 | 장기 운영과 검색 유입에 유리 |

### 1.3 핵심 문제

아래 A~D는 2026-08-02 기준 진단 기록이다. 2026-08-11 현재 A~C는 행사 중심
탐색·비교·실회차 아카이브로 수정됐고, D는 공식 원문 수집·해시·근거·재확인
대기열을 가진 결정적 생성 파이프라인으로 대체됐다. 남은 병목은 기능 유무가
아니라 참가 판단 가능한 필드의 밀도와 실제 반복 사용 증거다. E의 과도한 범위
확장 위험은 여전히 유효하다.

#### A. 제품의 첫 이유가 분산되어 있다

행사, 노트, 공동구매, 뉴스, 커뮤니티가 같은 무게로 보이면 사용자는
"여기서 가장 잘 해결되는 문제가 무엇인지" 즉시 이해하기 어렵다. 초기 제품은
기능의 폭보다 한 가지 문제의 압도적인 해결이 필요하다.

#### B. 실제 데이터보다 플랫폼 기능이 앞서 있다

커뮤니티와 운영 기능은 실제 서비스 수준에 근접했지만, 공개 행사 데이터는
예시 중심이다. 데이터가 적으면 비교, 아카이브, 검색, 추천, SEO가 모두 약해진다.

#### C. 회차 이력이 핵심 자산인데 독립 탐색 경로가 없다

행사 상세 안에는 이력이 존재하지만, 사용자가 "행사별 역대 변화"를 먼저
탐색하거나 여러 행사를 같은 표에서 비교하는 전용 화면은 없었다.

#### D. 콘텐츠 운영 체계가 코드 안의 수동 데이터에 머문다

행사 데이터가 `app/lib/data.ts`에 직접 들어 있어 초기 검증에는 단순하지만,
수십·수백 행사로 확장할 때 다음 문제가 발생한다.

- 확인 담당자와 확인 시점 관리가 어렵다.
- 출처 변경 이력과 수정 이유를 추적하기 어렵다.
- 운영자가 코드 배포 없이 데이터를 갱신할 수 없다.
- 만료·재확인 대상의 자동 대기열을 만들기 어렵다.

#### E. 장기 비전이 너무 빨리 `Creator OS`로 넓어질 위험이 있다

행사, 작가, 제작업체, 세금, 거래, AI 추천을 모두 동시에 만들면 어느 영역도
충분한 데이터 밀도를 만들지 못한다. Creator OS는 시작점이 아니라 행사 데이터
우위를 확보한 뒤의 결과여야 한다.

## 2. 전략적 선택

### 2.1 제품 카테고리

초기 카테고리는 `커뮤니티`나 `창작자 포털`이 아니라 다음으로 정의한다.

> **한국 독립 창작자 행사 데이터베이스 및 준비 아카이브**

영문 설명이 필요할 때는 `Creator Event Intelligence & Operations Archive`를
내부 표현으로 사용할 수 있다. 외부 카피는 한국어 사용자가 즉시 이해하도록
`행사 마감·조건·회차 아카이브`를 우선한다.

### 2.2 핵심 가치 제안

- 흩어진 공식 공지를 같은 필드로 비교한다.
- 현재 회차만이 아니라 과거 회차의 변화까지 남긴다.
- 정보마다 원문과 확인 시점을 제공한다.
- 가입하지 않아도 비교, 저장, 일정 구독을 사용할 수 있다.
- 경험 정보는 출처·표본 수·확인 상태와 함께 제한적으로 공개한다.

### 2.3 하지 않을 것

- 티켓 판매나 참가 신청을 중개하는 플랫폼
- 네이버 카페형 범용 자유게시판
- 작가 간 DM·직거래·정산 플랫폼
- 출처 없는 후기 점수와 순위 서비스
- 자동 수집 결과를 검수 없이 게시하는 행사 크롤러
- 행사 데이터가 충분하지 않은 상태에서의 범용 AI 챗봇

## 3. 사용자와 핵심 작업

### 3.1 1차 사용자

오프라인 문구·일러스트 행사 참가를 검토하거나 준비하는 한국의 1인 창작자와
소규모 굿즈 판매자다.

### 3.2 2차 사용자

- 첫 참가를 준비하는 예비 작가
- 여러 지역 행사를 비교하는 기존 참가자
- 공식 공지를 놓치지 않으려는 행사 운영 실무자
- 창작 행사와 작가를 탐색하는 문구·일러스트 소비자

### 3.3 Jobs to be Done

#### 지원 결정

> 여러 행사의 비용과 조건이 다를 때, 제한된 시간과 예산을 어디에 쓸지
> 판단할 수 있도록 같은 기준으로 비교하고 싶다.

필요 정보:

- 신청 마감과 마감 시각
- 참가비와 추가 비용
- 선정 방식과 사업자 필요 여부
- 부스 크기와 제공 집기
- 개최 지역·기간
- 공식 출처와 최종 확인일
- 과거 회차 대비 변경 내용

#### 참가 준비

> 참가가 확정되었을 때, 신청 자료부터 현장 철수까지 빠뜨리지 않고 준비하고 싶다.

필요 정보:

- 제출 자료
- 반입·철수 시간
- 전기·벽면·주차·물류
- 결제·재고·가격표 체크리스트
- 행사별 변경 공지

#### 경험 축적

> 행사가 끝난 뒤 다음 회차의 판단에 쓸 수 있도록 비용과 경험을 구조화해 남기고 싶다.

필요 정보:

- 실제 지출과 손익
- 방문객 밀도와 판매 성과
- 운영 난이도
- 재참가 의향
- 표본 수와 익명 공개 기준

## 4. 제품 구조

### 4.1 핵심 계층

```text
공식 공지·운영자 확인
        ↓
행사 마스터
        ↓
행사 회차 데이터
        ↓
비교 · 아카이브 · 달력 · Binder
        ↓
준비 노트 · 공식 소식
        ↓
질문 · 경험 · 정리 답변
        ↓
검증된 내용의 행사 데이터/노트 환류
```

### 4.2 정보 구조

#### 1차 내비게이션

- 행사
- 비교
- 회차 아카이브
- 준비 노트
- 내 바인더

제품의 첫 이유를 한 번에 이해할 수 있도록 1차 내비게이션 자체를 행사 중심
행동으로 바꾼다. 공식 소식과 커뮤니티는 푸터·모바일 보조 탐색에서 제공하고,
공동구매는 후단 정책 검토 전까지 숨긴다. 행사 내부의 주요 행동은 다음처럼
나눈다.

- `/events`: 현재 회차 검색과 필터
- `/events/compare`: 최대 3개 행사 조건 비교
- `/events/archive`: 행사별 회차 변화 탐색
- `/events/calendar`: 신청·개최 일정
- `/events/[slug]/[edition]`: 한 회차의 상세 판단

#### 홈

홈은 대시보드가 아니라 다음 세 가지 질문에만 답한다.

1. 지금 가장 가까운 마감은 무엇인가?
2. 어떤 행사를 비교할 수 있는가?
3. 과거 회차에서 무엇이 달라졌는가?

행사 검색·비교·회차 아카이브·준비 노트는 네 개 텍스트 인덱스로 유지하고,
뉴스·달력·커뮤니티는 보조 링크로 내린다. 첫 행동은
행사 비교와 회차 아카이브로 둔다.

### 4.3 커뮤니티의 역할

커뮤니티는 별도 성장 목표가 아니라 **데이터 공백을 발견하고 지식으로
승격시키는 입력 계층**으로 관리한다.

- 질문에는 관련 행사·분류·해결 상태를 붙인다.
- 사실 주장에는 출처와 확인 날짜를 붙일 수 있다.
- 해결된 공개 질문은 운영자가 Note로 승격할 수 있다.
- 반복적으로 확인된 정보는 행사 회차 데이터 수정 후보가 된다.
- 자유 대화는 허용하되 홈과 검색의 핵심 결과를 차지하지 않는다.

## 5. 행사 데이터 모델 발전안

### 5.1 마스터와 회차 분리

현재 `slug`와 `edition`, 내부 `history`를 사용하고 있다. 데이터가 늘기 전에
다음 구조로 명시적으로 분리해야 한다.

#### Event Master

- `id`
- 공식 행사명
- 약칭
- 운영사
- 공식 웹사이트·SNS
- 기본 장르
- 기본 개최 지역
- 활성/중단/종료 상태
- 대표 이미지와 이미지 권리 정보

#### Event Edition

- `id`
- `event_master_id`
- 회차명
- 신청 시작·마감 시각
- 개최 시작·종료 시각
- 장소와 주소
- 부스 유형별 가격
- 부스 수
- 선정 방식
- 사업자·통신판매업 요구 여부
- 제출 서류
- 환불·양도 기준
- 반입·철수·전기·벽면·주차·물류·집기
- 공식 출처 레코드
- 최종 확인 시각
- 이전 회차 대비 변경 요약

#### Source Record

- 원문 URL
- 출처 종류: 공식 사이트, 공식 SNS, 신청 폼, 참가자 안내문
- 확인 담당자
- 확인 시각
- 원문 발행·수정 시각
- 캡처 또는 해시
- 유효 기간
- 폐기·대체 관계

#### Aggregate Feedback

- 응답 수
- 비용 대비 만족
- 방문객 밀도
- 운영 난이도
- 재참가 의향
- 공개 가능 여부
- 수집 기간과 질문 버전

### 5.2 데이터 상태

각 회차는 최소 다음 상태를 가져야 한다.

| 상태 | 의미 | 공개 방식 |
|---|---|---|
| `draft` | 운영자 입력 중 | 비공개 |
| `needs-source` | 핵심 필드에 공식 근거 없음 | 제한 공개 또는 경고 |
| `verified` | 공식 출처와 확인 시점 존재 | 정상 공개 |
| `stale` | 유효 기간이 지나 재확인 필요 | 재확인 경고 |
| `superseded` | 더 최신 공지로 대체됨 | 이력으로 유지 |
| `archived` | 종료된 과거 회차 | 아카이브 공개 |

### 5.3 품질 지표

내부 운영 대시보드에서 다음을 측정한다.

- 필수 필드 완성률
- 공식 출처 연결률
- 최근 30일 내 확인률
- 마감 시각까지 포함된 비율
- 이전 회차 변경 요약 보유율
- 중복 행사·회차 후보 수
- 사용자 정정 제보의 평균 처리 시간

## 6. 화면별 개선안

### 6.1 홈

#### 유지

- 현재 날짜
- 마감 임박 3건
- 낮은 정보량
- 네 개 행사 중심 텍스트 인덱스
- 리소 4역할 색과 선형 정보 구조

#### 변경

- 제품 설명을 `행사 일정과 준비 기준`에서 `행사 회차·부스비·신청 조건을
  누적하는 아카이브`로 구체화한다.
- 1차 CTA를 `행사 비교하기`로 둔다.
- 2차 CTA를 `회차 아카이브 보기`로 둔다.
- 캘린더 구독은 행사/달력 화면에서 제공한다.

### 6.2 행사 목록

- 필터와 마감 중심 구조는 유지한다.
- 상단에 비교·아카이브·달력으로 가는 명시적 경로를 둔다.
- 장기적으로 다음 필드를 목록에 추가한다.
  - 지난 회차 대비 참가비 증감
  - 마지막 확인일
  - 정보 완성도
  - 후기 표본 수
- 모바일에서는 모든 필드를 노출하지 않고 사용자가 정렬 기준을 고르게 한다.

### 6.3 행사 비교

초기 버전은 최대 3개 행사를 서버 렌더링 GET 폼으로 비교한다.

비교 필드:

- 신청 마감
- 개최 일정
- 지역·장소
- 참가비
- 부스 크기·부스 수
- 선정 방식
- 사업자 필요 여부
- 제출 자료
- 전기·제공 집기
- 공식 정보 확인일

향후 URL에 선택 상태를 보존하고, Binder에서 저장한 행사를 바로 불러오며,
필드 차이만 강조하는 모드를 추가한다.

### 6.4 회차 아카이브

행사 마스터별로 회차를 묶어 다음 변화를 한 표에서 보여 준다.

- 일정
- 장소
- 참가비
- 부스 수
- 선정 방식

향후 회차별 포스터, 공지 변경 이력, 신청 조건 변화, 운영 노트를 추가한다.

### 6.5 행사 상세

현재 상세 구조는 좋은 기반이다. 다음 순서로 강화한다.

1. 현재 회차 핵심 사실
2. 공식 원문과 확인 시점
3. 이전 회차 대비 변경점
4. 신청 준비
5. 현장 준비
6. 회차 이력
7. 집계 후기
8. 관련 노트·질문·공식 소식

장기적으로 페이지 제목을 행사 마스터와 회차로 시각적으로 분리하고, 행사
마스터 페이지와 회차 페이지를 별도 URL로 나눈다.

### 6.6 노트

블로그가 아니라 유지보수 가능한 Knowledge Base로 운영한다.

각 노트는 다음을 갖는다.

- 적용 대상과 적용하지 않는 대상
- 최종 확인일
- 공식 출처
- 단계별 체크리스트
- 관련 행사와 관련 질문
- 오래된 정보 경고
- 변경 이력

### 6.7 이미지

현재 정보 우선 방향은 맞지만, 실제 운영 단계에는 다음 이미지가 필요하다.

- 공식 행사 포스터 또는 대표 이미지
- 행사장·부스 참고 사진
- 공식 배치도
- 이전 회차 포스터 타임라인

이미지는 정보 판단을 보조해야 하며 카드 장식으로 사용하지 않는다. 각 이미지에
출처, 권리 상태, 회차, 확인 날짜를 기록한다. 권리 확인이 안 된 이미지는
썸네일을 재배포하지 않고 공식 원문 링크만 제공한다.

## 7. 데이터 운영 방식

### 7.1 수집 원칙

- 자동 수집은 후보를 만들 뿐 공개를 확정하지 않는다.
- 신청 마감·비용·환불·사업자 조건은 공식 원문을 필수로 한다.
- SNS 게시물만 존재하면 게시물 URL과 확인 시점을 함께 저장한다.
- 사용자가 제보한 정보는 운영자 확인 전까지 별도 상태로 둔다.
- 정보가 없으면 추정하지 않고 `정보 없음` 또는 `확인 중`으로 표시한다.

### 7.2 주간 운영 루틴

#### 매일

- 14일 이내 마감 행사 변경 공지 확인
- 사용자 정정 제보와 깨진 공식 링크 확인

#### 매주

- 신규 행사 후보 검토
- 30일 내 마감 예정 행사 일괄 재확인
- 종료 행사 아카이브 전환
- 이전 회차 대비 변경 요약 작성
- 검색 유입이 있는 빈 결과와 미등록 행사 확인

#### 매월

- 데이터 완성률과 오래된 출처 보고
- 행사 마스터 중복 정리
- 주요 노트 재검토
- 후기 집계의 N 기준과 익명성 점검

### 7.3 운영 도구 단계

1. 코드 기반 수동 데이터에서 시작
2. 검증된 YAML/JSON 콘텐츠 저장소로 분리
3. 운영자 전용 입력·검수 화면 도입
4. 출처 변경 감지와 재확인 대기열 추가
5. 제보 → 검수 → 공개 → 이력 보존 워크플로 구축

Supabase를 사용할 경우 커뮤니티 스키마와 행사 콘텐츠 스키마를 분리하고,
공개 읽기와 운영자 변경 권한을 별도 정책으로 둔다.

## 8. 검색·유입 전략

### 8.1 검색 랜딩 단위

- 행사 마스터: `서울일러스트레이션페어 일정·부스비·역대 회차`
- 행사 회차: `서울일러스트레이션페어 2026 겨울 신청 마감`
- 비교: `서일페 vs 일러스타페어 부스비 비교`
- 지역·장르: `부산 문구 행사`, `비사업자 참가 가능 일러스트 행사`
- 준비 노트: `첫 부스 준비물`, `행사 손익분기 계산`
- 공식 변경: `행사 부스비 인상`, `신청 조건 변경`

현재 Event·Article JSON-LD 기반을 유지하고 다음을 검토한다.

- 행사 마스터와 회차의 canonical 관계
- BreadcrumbList
- FAQPage는 실제 FAQ와 답변이 있을 때만 사용
- Dataset 또는 ItemList는 검색엔진 정책과 실제 콘텐츠 표현을 확인한 뒤 사용

### 8.3 재방문 채널

- ICS 일정 구독
- RSS
- Binder 저장
- 저장 행사 마감 알림
- 지역·장르별 새 행사 알림
- 회차 변경 알림

이메일은 인앱 알림과 별도 동의·해지·발송 정책이 준비된 뒤 추가한다.

## 11. 실행 로드맵

### Phase 0 — 전략 정렬과 탐색 경로 구축

상태: 이 변경에서 1차 구현

- [x] 제품 포지셔닝을 행사 아카이브 중심으로 명시
- [x] 홈 CTA를 비교·회차 아카이브 중심으로 변경
- [x] `/events/compare` 추가
- [x] `/events/archive` 추가
- [x] 행사 목록에서 비교·아카이브·달력 진입 제공
- [x] sitemap과 README 경로 갱신
- [x] 장기 전략·데이터 운영·지표·로드맵 문서화

완료 기준:

- 사용자가 홈에서 한 번의 선택으로 비교 또는 회차 이력에 접근한다.
- 비교 상태가 URL 쿼리로 공유된다.
- 신규 공개 경로가 sitemap에 포함된다.
- 기존 커뮤니티·권한 경계는 변경하지 않는다.

### Phase 1 — 실제 데이터 기반 만들기

권장 기간: 0~6주

- [ ] 행사 마스터와 회차 스키마를 분리
- [ ] 예시 행사와 실제 검증 행사를 명시적으로 분리
- [ ] 최소 50개 행사 마스터와 120개 회차 입력
- [ ] 공식 출처·확인 시점·확인 담당자 필드 도입
- [ ] 재확인 필요 상태와 운영 대기열 정의
- [ ] 행사별 포스터·이미지 권리 메타데이터 정의
- [ ] 비교 URL의 선택·중복·빈 상태 브라우저 테스트 추가
- [ ] 아카이브의 회차 정렬과 중복 제거 도메인 테스트 추가

출시 게이트:

- 마감, 참가비, 장소, 선정 방식은 공식 출처가 없으면 검증 상태로 공개하지 않는다.
- 현재 회차의 90% 이상이 최근 확인일을 가진다.
- 모바일에서 비교 표는 페이지가 아니라 표 컨테이너만 가로 스크롤한다.

### Phase 2 — 운영 도구와 재방문 루프

권장 기간: 2~4개월

- [ ] 운영자 행사 입력·검수·수정 이력 화면
- [ ] 출처 URL 변경 감지와 링크 장애 확인
- [ ] Binder 기반 마감·변경 인앱 알림
- [ ] 지역·장르·사업자 조건 저장 검색
- [ ] 행사 마스터 페이지와 회차 페이지 분리
- [ ] 이전 회차 대비 자동 diff 초안과 운영자 승인
- [ ] 사용자 정정 제보 → 검수 → 공개 워크플로

출시 게이트:

- 모든 공개 수정은 작성자·시각·사유를 남긴다.
- 자동 감지는 직접 공개하지 않고 운영자 검수 대기열만 만든다.
- 알림은 사용자가 명시적으로 저장하거나 구독한 조건만 대상으로 한다.

### Phase 3 — 지식 그래프와 경험 데이터

권장 기간: 4~9개월

- [ ] 행사 ↔ 노트 ↔ 커뮤니티 질문 ↔ 공식 소식 연결
- [ ] 표본 N 기준을 지킨 구조화 후기 수집
- [ ] 행사별 비용·손익 템플릿
- [ ] 제작업체·인쇄 방식·포장재 지식 카탈로그
- [ ] 행사 변경 타임라인
- [ ] 검증된 답변의 데이터·노트 승격 제안

출시 게이트:

- 개인을 추정할 수 있는 소표본 지표는 공개하지 않는다.
- 후기와 공식 사실을 같은 시각 신호로 표시하지 않는다.
- 업체 정보에는 광고·제휴·편집 관계를 명시한다.

### Phase 4 — 개인화와 AI

권장 기간: 9~18개월

- [ ] 조건 기반 행사 추천
- [ ] 예산·지역·사업자 상태·상품 유형을 반영한 준비 계획
- [ ] 공식 원문 변경 요약
- [ ] Binder와 과거 참가 기록 기반 일정 제안
- [ ] 운영자용 중복·이상값·누락 탐지

AI 출시 게이트:

- 추천 근거 필드와 제외 이유를 사용자에게 설명한다.
- 원문이 없는 사실을 생성하지 않는다.
- 세금·법률·환불 안내는 공식 출처와 확인 날짜를 함께 보여 준다.
- 추천 품질을 평가할 실제 데이터와 실패 사례가 충분히 쌓인 뒤 공개한다.

## 13. 이번 구현의 기술 범위

이번 변경은 데이터베이스 마이그레이션이나 커뮤니티 권한 코드를 건드리지 않는다.
기존 정적 행사 컬렉션을 읽어 두 개의 공개 탐색 화면을 추가한다.

### 추가 경로

- `/events/compare`
  - GET 쿼리 `event1`, `event2`, `event3`
  - 최대 3개 행사를 같은 표에서 비교
  - 중복 선택은 한 열로 합침
- `/events/archive`
  - 동일 `slug`를 행사 마스터 후보로 묶음
  - 각 이벤트 레코드의 `history`를 회차 표로 노출
  - 최신 회차 상세로 연결

### 변경 경로

- `/`
  - 행사 아카이브 중심 설명과 CTA
- `/events`
  - 비교·아카이브·달력 진입
- `/sitemap.xml`
  - 신규 공개 경로 포함

### 의도적으로 제외한 범위

- 데이터 스키마 마이그레이션
- 외부 Supabase 연결
- 실제 행사 데이터 수집
- 커뮤니티 정책 변경
- 이미지 다운로드·재배포
- 광고·결제·정산

## 14. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 행사 정보 오류 | 사용자의 비용·일정 판단 실패 | 공식 원문, 확인 시점, 재확인 상태, 정정 이력 |
| 운영량 과다 | 최신성 하락 | 행사 수보다 필수 필드·마감 임박 행사 우선 |
| 커뮤니티가 제품 중심을 잠식 | 정보 탐색 약화 | 홈·검색·SEO는 행사 우선, 커뮤니티는 관련 맥락에 연결 |
| 이미지 저작권 | 재배포 분쟁 | 권리 메타데이터, 불명확하면 원문 링크만 제공 |
| 이름 충돌 | 브랜드·도메인 혼선 | 영구 도메인 전 상표·앱·서비스명 조사와 대안명 확보 |
| 자동 수집 오류 | 잘못된 정보 대량 공개 | 자동화는 후보 생성만, 공개 전 사람 검수 |
| 과도한 기능 확장 | 데이터 밀도 부족 | 단계별 데이터 수 기준을 다음 기능의 진입 조건으로 사용 |

## 15. 최종 방향

Bindery는 장기적으로 창작자의 운영 도구가 될 수 있다. 다만 그 순서는
반드시 다음과 같아야 한다.

```text
행사 데이터 밀도
→ 회차 비교와 신뢰
→ 저장·알림·준비 도구
→ 구조화된 경험과 지식
→ 제작·사업 운영 데이터
→ 개인화와 AI
```

따라서 다음 6주 동안 가장 중요한 작업은 새로운 커뮤니티 기능이나 대형 AI
기능이 아니라, **실제 행사 50개와 회차 120개를 공식 출처와 함께 축적하고
비교·아카이브 화면의 사용성을 검증하는 것**이다. 이 기준을 통과한 뒤에만
Creator OS라는 장기 비전을 제품 기능으로 넓힌다.
